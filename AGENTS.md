# Agent instructions

- This repository is the source of truth. Keep the device contract transport-agnostic, versioned, and backwards compatible.
- Treat manufacturer-documentation-backed facts, simulated behavior, compiled firmware, and bench-verified behavior as different evidence levels. Never call simulation a physical verification.
- First reference board: Seeed XIAO ESP32S3 Sense SKU 113991115. Confirm camera module revision when purchased.
- Do not claim unimplemented hardware capabilities in the runtime device manifest. Keep planned and active capabilities separate.
- Never guess PCB traces, battery pin polarity, charger behavior, pin allocation, power consumption, sensor accuracy, or shipping prices.
- Hardware module profiles require exact vendor/product, primary documentation, I2C addresses, logic voltage, wiring, and known limitations. Reuse standard buses and existing upstream drivers.
- Preserve security boundaries. Localhost simulator is development-only; never expose unauthenticated control on the LAN or public internet.
- If BLE is added or changed, require device authorization, reconnection/error behavior, permission handling, and explicit security review before enabling media or commands with side effects.
- Write tests for new protocol types, module combinations, and failure paths. Verify using Python unit tests before publishing.
- Keep modules small and independent. Avoid introducing cloud accounts, unnecessary services, complex frameworks, or autogenerated abstractions.
- For physical development, follow order: USB + button -> BLE connection -> IMU -> camera stills -> microphone -> Wi-Fi media -> protected LiPo battery -> enclosure.
- The Android application remains a separate codebase. Provide an adapter interface; do not rewrite Personal Voice without inspecting that repository.
- Avoid assuming that Qwiic makes the whole system automatically discoverable. Detection is limited to address/identity checks for known compatible devices, and requires safe electrical wiring.
